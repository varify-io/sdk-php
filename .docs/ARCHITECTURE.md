# Architecture

How the SDK assigns and tracks a visitor. The reasoning behind each decision is in the [PHP & Shopware SDK v1 plan](https://claude.ai/artifact/JgkbbQ4FhshMyvw5c7aT9V).

## Packages

- **`varify-io/core`** knows nothing about frameworks: it loads the config, parses untrusted input, evaluates assignments and renders the tracking snippet. Its only dependency is the `psr/simple-cache` interface. It never throws into a render: every failure ends in "show the original, track nothing".
- **`varify-io/shopware`** (planned) owns everything Shopware-specific: the request subscriber, the HTTP cache key, Twig functions and settings.

An integration builds on `core` and doesn't reach into another integration.

## A request

```
request ──▶ Varify::forRequest() ──▶ templates call assignment() ──▶ trackingSnippet() ──▶ varify.js ──▶ tracking provider
                 │
                 ├─ BotDetector: bots get no id and the original
                 ├─ ConfigLoader: PSR-16 cache, else Transport (curl, 300 ms); last good config on failure
                 ├─ CookieCodec: decode the `varify` cookie (anonymous when missing or malformed)
                 └─ Evaluator: forced, then stored, then bucketed
```

1. **The integration** builds a `VarifyRequest` (cookie value, `varify-force`, user agent) and calls `Varify::forRequest()` once, before rendering. When `needsCookieWrite()` is true it writes `cookieValue()` and makes sure no shared cache stores that response. `Varify::fromGlobals()` does this for plain PHP.
2. **Rendering** reads `assignment($experimentId)`. Each first read of an experiment is recorded as an exposure.
3. **Tracking** happens in the browser: `trackingSnippet()` hands the exposures to `window.varify.trackServerSide`, or queues them in `window.varify.serverSideQueue` until varify.js loads. varify.js applies consent and the team's dataSaveMode.

## The config

`https://delivery.varify.io/ss/{teamId}.json`, regenerated by laravel-spark whenever an experiment changes. PHP keeps nothing between requests, so the config goes through a PSR-16 cache (fresh entry with a TTL, plus a last-good copy without one). A failed load reports to `onError` and falls back to the last good config, else to `Config::unavailable()`: stored assignments are kept, nothing is assigned or tracked. `ConfigParser` turns the JSON into typed objects; anything unexpected is `invalid-config`.

## Assignment

Forced, then stored, then bucketed. The bucket is `murmur3("{experimentId}:{visitorId}", seed 1) / 2³² × 100`, which PHP computes with `hash('murmur3a', …, ['seed' => 1])`. It has to match varify-sdk-js exactly; `BucketTest` holds the shared reference values.

## The cookie

`{uid}.{experimentId}-{variationId}_…`: a UUIDv4, then one entry per experiment sorted by id, with variation `0` for the original. httpOnly, SameSite=Lax, 400 days. Byte-identical to varify-sdk-js, so both SDKs can share it across subdomains. `CookieCodec::decode()` turns anything malformed into an anonymous state, which gets a new id.
